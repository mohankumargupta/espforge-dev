# Better architecture: making "add a component or device" a one-file change

## 1. The problem, measured

Adding one simple GPIO-backed component (call it `<buzzer>`) today means editing roughly this:

| # | Crate / file | What you touch |
|---|---|---|
| 1 | `espforge-espgenerate-template/espf.schema.kdl` | the `element` node (the intended single source of truth) |
| 2 | `espforge-bindings/.../generated_elements.rs`, `generated_vocab.rs` | regenerated by `build.rs`, **committed**, CI diffs them |
| 3 | `espforge-options/.../generated_catalog.rs` | regenerated by a second `build.rs`, **committed** |
| 4 | `espforge-model/src/board.rs` | new struct, `Component` variant, `Component::id()` arm, `OwnerKind` variant, `OwnerKind::tag()` arm |
| 5 | `espforge-hardware/src/board.rs` | match arm in `build`, a `buzzer_node` fn, a `buzzer_issue` fn, the hard-coded "(only `<led>`, `<button>`, ...)" string, possibly arms in `pin_conflict` |
| 6 | `espforge-diagnostics/src/codes.rs` | new constants, new arms in `for_message`, new entries in the test title list |
| 7 | `espforge-core/src/board_json.rs` | arm in `component_value` |
| 8 | `espforge-emit/src/codegen/rust.rs` | arm in `generated()` (field + init) **and** arm in `safety_comments()` |
| 9 | `espforge-emit/src/codegen/overlay.rs` | arm in `resolve_token` for `{{ x.pin }}` |
| 10 | `espforge-runtime` | the runtime type, plus a re-export in `lib.rs` behind a long `cfg(any(target_arch...))` |
| 11 | `espf/src/context.rs` | only if the link attribute is new (it hard-codes `i2c`/`spi`/`gpio`/`uart`) |
| 12 | tests and docs | golden `MATRIX`, the `CELLS` constant, golden dirs, diagnostics corpus + snapshots that quote the "(only ...)" string, transcripts, example dir, README table |

That is about 9 of 12 workspace crates and 20+ edit sites for one element. The Rust compiler helps only partly, because several of these are string matches, not exhaustive enum matches.

## 2. Root causes

**A. The code is sliced by layer; the feature is a vertical slice.**
Every element has the same life cycle (declare → validate → lower → claim resources → serialize → emit Rust → emit Cargo/Wokwi bits). Each stage is a `match` over the element kind, living in a different crate. This is the classic expression problem: adding a *variant* touches every *operation*.

**B. There are several sources of truth for "what an element is".**
The KDL schema already declares tag, attributes, kinds, ranges, defaults, `ref to=`, choices and examples. It is then re-declared by hand in:
- `Refs::resolve` (`a.key == "i2c" || "spi" || "gpio" || "uart"`, and `key.contains("component")` for devices),
- `PeripheralKind` in `espf`,
- one `*_issue` / `describe` function per element, mapping the generated `Issue` to wording,
- the "supported by `build` yet (only ...)" lists, repeated in `board.rs` (twice) and `devices/mod.rs`, and baked into snapshot files,
- `status="planned"` in the KDL (note: `wifi` is marked planned but `board.rs` builds it).

**C. The KDL is parsed four times.**
`catalog.rs`, `schema.rs`, and two `build.rs` files (`espforge-options`, `espforge-bindings`) each contain their own KDL walking code (`option_literal`, `element_literal`, `attr_literal`, `kind_literal`, `element_module`, ...). `espforge-options/build.rs` exists only to precompute what `catalog::load` and `schema::load` already compute (they are tiny; parsing at first use costs microseconds). Both `build.rs` files also **write into `src/`**, which fights `cargo publish` verification and is why CI needs a `git diff --exit-code` guard and why generated code is committed.

**D. Diagnostic codes are assigned by string-matching the human title.**
`EspfError::to_diagnostic` calls `for_message(&self.title)`. Reword a title, or forget a new arm, and you silently get `E0999`. Codes are a public JSON contract, yet they derive from prose.

**E. The runtime and the code generator are connected only by strings.**
`rust.rs` emits `espforge_runtime::Led::new(...)` as tokens. Nothing ties that to the runtime's actual API except the ignored `generated_projects_compile` test. Related drift: the runtime's `I2cBus::build` takes a concrete `I2C0<'static>` and `SpiBus::build` a concrete `SPI2<'static>`, while the lowering accepts `i2c1`/`i2c2` and emits `I2C1`/`I2C2`, which cannot compile.

**F. Devices are scaffolding, not a mechanism.**
`route_driver(tag, node) -> Result<(), String>` is generated from file names in `src/drivers/`, and every driver's `init` is a no-op. Meanwhile `devices::reject_if_present` rejects any non-empty `# devices` section, so as far as I can tell `06.Displays/ili9341_example` cannot pass `espforge check` today, and `ssd1306_example` has neither a schema element nor a driver. Adding a device has no real path yet, which is the best moment to design one.

**G. Tests hard-code the world.**
`MATRIX` (30 cells), `CELLS = 30`, the compile matrix, and hand-listed transcript cases all need updating when something is added.

## 3. Target design: slice by element, not by layer

### 3.1 One module per element, one registry line

Create a host-side crate (name suggestion: `espforge-elements`) with one file per element:

```
espforge-elements/src/
  lib.rs              // the registry: ONE line per element
  kind.rs             // Element trait, LowerCx, EmitCx
  peripherals/        gpio.rs  i2c.rs  spi.rs  uart.rs
  components/         led.rs   button.rs  i2c_component.rs  spi_component.rs  uart_component.rs
  devices/            ili9341.rs  tmp102.rs  status_led.rs
  services/           wifi.rs
```

Everything the element needs lives in its file:

```rust
pub struct Led;

impl Element for Led {
    const TAG: &'static str = "led";        // must match a schema element (tested)

    fn lower(node: &ParsedNode, cx: &mut LowerCx) -> Result<(), ()> {
        let a = cx.attrs::<led::Attrs>(node)?;     // generated typed attrs + generic issue->diagnostic
        let gpio = cx.gpio(&a.gpio)?;              // reference resolved by the schema's `ref to="gpio"`
        let pin  = cx.claim_pin(gpio.pin, PinUse::Output, node)?;
        cx.push(LedLowered { id: cx.ident(node), pin, active_low: a.active_low.value });
        Ok(())
    }
}

impl Lowered for LedLowered {
    fn id(&self) -> &Ident { &self.id }
    fn json(&self, _b: &Board) -> Value { json!({ "kind": "led", "pin": self.pin.pin().0, /* ... */ }) }
    fn emit(&self, _b: &Board, cx: &mut EmitCx) {
        let (name, pin, low) = (self.field(), gpio(self.pin.pin().0), self.active_low);
        cx.field(quote!(pub #name: espforge_runtime::Led,));
        cx.init(quote!(#name: espforge_runtime::Led::new(#pin, #low),));
        cx.safety_comment(format!("{name}: espforge_runtime::Led::new("),
                          format!("SAFETY: espforge checked that no other component uses GPIO{}.", self.pin.pin().0));
    }
    fn overlay_attr(&self, attr: &str) -> Option<String> {   // `{{ red_led.pin }}`
        (attr == "pin").then(|| self.pin.pin().0.to_string())
    }
}
```

The registry is the only shared place:

```rust
pub const ELEMENTS: &[&dyn ElementDyn] = &[
    &Gpio, &I2c, &Spi, &Uart,
    &Led, &Button, &I2cComponent, &SpiComponent, &UartComponent,
    &StatusLed, &Ili9341, &Tmp102,
    &Wifi,
];
```

`board::build`, `board_json::value`, `rust::generated`, `overlay::resolve_token`, `safety_comments`, `cargo::manifest` and the supported-elements error text all become **loops over the registry** (or over `Board.components` calling trait methods). No per-element `match` remains outside the element's own file.

### 3.2 `EmitCx` solves the awkward cases

The hard part of emitting is shared things: the SPI bus `let` must be emitted once per *used* bus, Cargo features depend on what is present, Wi-Fi needs a heap. Give the context memoizing helpers instead of cross-element `match`es:

```rust
cx.once("spi2_bus", || quote!{ let spi2_bus = espforge_runtime::SpiBus::build(...)...; });
cx.cargo_feature("esp-radio", "wifi");        // collected, then cargo.rs renders
cx.runtime_feature("wifi");
cx.needs_heap();                               // replaces `opts.is_on("wifi") || opts.is_on("ble-trouble")`
```

### 3.3 Keep exhaustiveness where it is cheap

A closed `enum Component` gives exhaustive `match` and free `Clone/PartialEq`; trait objects give open extension. Two reasonable options:

- **Option 1 (recommended first step): keep the enum, generate the dispatch.** Use a one-line-per-variant macro (or the `enum_dispatch` crate) so `Component` forwards `Lowered` methods to each variant. Adding a variant = add the struct + `impl Lowered` + one macro line. You keep exhaustiveness, `Clone`, `PartialEq`, and the existing model tests.
- **Option 2: `Box<dyn Lowered>`** (with `dyn-clone` and `as_any`). Truly open, but you give up derived `PartialEq` on `Board` and exhaustiveness. Only worth it if third-party elements become a goal.

Either way, replace the exhaustiveness you lose with a **contract test** (section 6).

### 3.4 Make the schema actually single-source

Everything below is already data in the KDL or trivially added to it:

| Today (hand-coded) | Derive from |
|---|---|
| `Refs::resolve` hard-codes `i2c`/`spi`/`gpio`/`uart` and `key.contains("component")` | each attr's `ref to="..."` (already in the schema) |
| `PeripheralKind` enum | elements whose `section="peripherals"` |
| `led_issue`, `button_issue`, `describe` per element | one generic `issue_to_diagnostic(&ElementDef, Issue)`; optional `message="..."` on `attr` for wording overrides |
| "(only `<gpio>`, `<i2c>`, ...)" strings | `ELEMENTS.iter().filter(section).map(tag)` |
| `status="planned"` | "is there a registry entry?" (test: planned ⇔ unregistered) |
| `NOT_YET_SUPPORTED` in `chips.rs` **and** `doctor.rs` | one constant in `chips.rs` |
| `has_usb_serial_jtag` list | an `esp-metadata-generated` query, or a column in the schema |
| `RUNTIME_VERSION = "0.6.0"` | `env!("CARGO_PKG_VERSION")` of the runtime crate / workspace version |

### 3.5 Typed diagnostic codes, no title matching

```rust
// before
EspfError::at_node(n, "invalid led", msg)          // code guessed later from the title
// after
Diag::at_node(codes::COMPONENT_INVALID_LED, n, "invalid led", msg)
```

Delete `for_message`, `dynamic_code`, and the 70-entry title table. `codes.rs` stays as plain constants (that file is the public contract), and a test asserts every constant is unique, well formed, and referenced. `E0999` disappears as a possible runtime outcome. Reserve a numeric block per section so contributors do not collide.

### 3.6 Drop build-time codegen that does not earn its keep

- Delete `espforge-options/build.rs`, `generated_catalog.rs`, `generated_options.rs` and the "generated table equals loader" tests. Replace with `LazyLock::new(|| load(SCHEMA_KDL).expect("embedded schema is valid"))`; a unit test already guarantees it loads.
- Keep one generator only: the typed `Attrs` structs in `espforge-bindings` (that is real compile-time value). Write it to `OUT_DIR` and `include!` it. Stop writing into `src/`, delete `generated_*.rs` from git, and drop the CI `git diff --exit-code` step.
- Make the generator the only code that interprets `kind`/`range`/`default`; share the KDL walking helpers with `catalog.rs` by moving the schema model (`ElementDef`, `AttrDef`) to a tiny `espforge-schema` crate that both the loader and `build.rs` depend on. Four KDL walkers become one.

### 3.7 Make devices a real mechanism

A device is "a driver bound to a component". Give it the same trait plus a binding declaration in the schema:

```kdl
element "tmp102" section="devices" {
    binds "i2c_component"                 // replaces the ad-hoc `i2c_component="$x"` / `component="$x"` naming
    runtime_item "espforge_drivers::Tmp102"
    cargo_dep "tmp102-driver" "0.1"       // collected by EmitCx
    ...
}
```

and in `ili9341.rs`: `lower` resolves the bound `spi_component`, claims `dc`/`rst`/`cs`, `emit` adds a `Devices` field and constructor. Then delete `route_driver`, `drivers/generated_registry.rs`, the directory-scanning `build.rs`, and `devices::reject_if_present`. The `every_routed_driver_has_a_devices_entry` test becomes "every registry element has a schema element" (one generic test).

### 3.8 Let the runtime be generic over peripheral instances

Change `I2cBus::build` / `SpiBus::build` to accept `impl esp_hal::i2c::master::Instance + 'static` (as `UartDevice::build` already does), so `i2c1`/`spi2`/etc. work and codegen stops needing to know concrete types. Put the repeated `#[cfg(any(target_arch = "riscv32", target_arch = "xtensa"))]` on a single `mod hw { ... }` and re-export from there with one `pub use hw::*;`. Adding a runtime component then needs one file and one `pub use`.

## 4. Testing becomes automatic

1. **Auto-discovered golden matrix.** Generate cells from `espforge_examples::categories()` × `offered_chips()` × runtimes the example supports (declare `runtime`/`chips` in the example, or default to its own). `MATRIX`, `CELLS`, and the slug list disappear. Keep the golden trees committed and `UPDATE_GOLDENS=1` as is; they are an excellent safety net.
2. **Per-element contract test, generated from the schema.** For every registry element and each of its schema `example` fragments: wrap it in a minimal valid file, `check` it, lower it, run codegen, parse the output with `syn`, assert `json()` and `overlay_attr` do not panic, assert all emitted codes are registered. Adding an element with at least one example gets all of this for free, and it replaces the exhaustiveness you gave up in 3.3.
3. **Schema ⇔ registry coherence test.** Every schema element has a registry entry unless it is `planned`; every registry entry has a schema element; every `ref to=` target exists.
4. **Diagnostics corpus stays**, but the "(only ...)" text is derived, so it changes only when support truly changes.
5. Keep the ignored compile test, and add the cheap half of it as a normal test: assert every `espforge_runtime::X` path an emitter mentions exists, by having each `emit` declare its `runtime_items()` and checking them against a `RUNTIME_EXPORTS` list the runtime crate publishes.

## 5. After: what adding `<buzzer>` costs

| # | Where | What |
|---|---|---|
| 1 | `espf.schema.kdl` | the `element` node, with at least one `example` |
| 2 | `espforge-elements/src/components/buzzer.rs` | `lower` + `json` + `emit` + `overlay_attr` |
| 3 | `espforge-elements/src/lib.rs` | one registry line |
| 4 | `espforge-runtime/src/components/buzzer.rs` + one `pub use` | the runtime type |
| 5 | `espforge-examples/src/examples/<cat>/buzzer/` | an example (auto-enters goldens and the contract test) |
| 6 | `espforge-diagnostics/src/codes.rs` | new constants, only if it has new error kinds |

From ~12 places across 9 crates to 4 to 6 places across 3 crates, with the checks that matter enforced by generic tests rather than by memory.

## 6. Migration plan (each phase keeps goldens byte-identical)

**Phase 0 — Baseline.** Add `buzzer` on the current code as a throwaway branch, count the edit sites, keep it as a regression metric. Confirm the goldens, diagnostics and transcripts are green.

**Phase 1 — Pure deletions (low risk, high value).**
- Remove `espforge-options/build.rs` + `generated_catalog.rs` + `generated_options.rs`; load the KDL lazily.
- Move the bindings output to `OUT_DIR`; delete committed generated files and the CI diff step.
- One `NOT_YET_SUPPORTED`; version constant from Cargo.
- Derive the "supported elements" strings from the catalog (update the affected diagnostics snapshots once with `UPDATE_DIAGNOSTICS=1` and review).

**Phase 2 — Typed diagnostic codes.** Thread `DiagCode` through `EspfError`, then delete `for_message`. Mechanical; the existing "every title has its own code" test turns into "every constant is unique and used".

**Phase 3 — Schema-driven references.** Rewrite `Refs::resolve` over `ref to=` and section membership; drop `PeripheralKind`. Add the schema ⇔ registry coherence test (initially against the existing `generated_elements` list).

**Phase 4 — Pathfinder element.** Introduce `Element`, `LowerCx`, `EmitCx`, the registry, and the Option 1 enum dispatch. Migrate **`led` only**, end to end (lower, json, emit, overlay). Goldens for `01.Basics.blink.*` must not change. Then migrate `button`, then buses (`i2c`, `spi`, `uart` and their components, which exercise `once()` and cross-element state), then `wifi`. Delete each old `match` arm as you go; when the last arm is gone, delete the `match` itself.

**Phase 5 — Devices.** Implement `binds`, migrate `tmp102` first (simplest), then `ili9341`; remove `reject_if_present` and the stub registry; add the missing `ssd1306` element or remove its example.

**Phase 6 — Tests and runtime.** Auto-discovered golden matrix; per-element contract test; generic `Instance` bounds and the single `cfg` module in the runtime.

## 7. Risks and trade-offs

- **Fewer compile-time guarantees with an open registry.** Mitigated by Option 1 (keep the enum) and the contract tests in section 4.
- **A new crate and a trait add indirection.** Offset by deleting four KDL walkers, two build scripts, and about five per-layer `match`es.
- **Message wording.** Generic issue messages will differ from the hand-tuned ones. Preserve exact text with an optional `message=` in the KDL where it matters; otherwise accept one reviewed snapshot update.
- **Emit ordering.** Shared prelude code (buses) must keep the exact order the goldens expect; `EmitCx::once` should append in first-use order, and the goldens will tell you immediately if not.
- **Do not** build a dynamic plugin system or proc-macro DSL. The goal is "one file per element in this repo", not external extensibility.

## 8. Smaller defects noticed along the way (worth fixing in passing)

- `I2cBus::build` / `SpiBus::build` take concrete `I2C0` / `SPI2` types, yet lowering allows `i2c1`/`i2c2` (see 3.8).
- `wifi` and `ntp` are `status="planned"` in the schema though `wifi` builds.
- `05.Networking/wifi/http_example` is nested one level too deep to be discovered as an example and uses syntax that no longer exists (`<wifi>` under `# peripherals`, `<http>` component).
- `ssd1306_example` references a device (`ssd1306`) that has no schema element or driver.
- Golden coverage is esp32c3 and esp32s3 only, so options and `rust-toolchain` paths for other chips are untested.
- The schema says pins "must be valid for the chosen chip", but no code checks pin validity against the chip.
